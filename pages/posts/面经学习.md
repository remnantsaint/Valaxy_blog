### 计算机网络

#### 办公室 Wiki 卡顿，人员集中时明显，如何排查与优化？
我会先确认哪些人、哪些操作变慢，再对比同一台电脑使用 Wi-Fi 和网线访问的速度，初步判断是办公网络拥堵，还是服务器处理慢。

如果只有 Wi-Fi 慢，重点检查无线设备连接人数、信号干扰；如果有线也慢，就结合网络和服务器监控，检查出口带宽、服务器资源，以及数据库查询和请求排队情况。

找到瓶颈后，再调整无线网络、优化带宽使用，或优化数据库查询、增加缓存和服务器容量，最后对比高峰期的响应时间和错误率，确认优化有效。

#### 企业网络高可用设计常用的四种冗余手段？

可以从设备、链路、路由和电源四个方面回答：

1. **设备冗余**：关键交换机、路由器或防火墙部署两台，通过主备或集群方式，在一台故障时由另一台接替。
2. **链路冗余**：关键设备之间部署多条连接，通过链路聚合或备用链路，避免单条线路故障导致中断。
3. **路由冗余**：设计多条可达路径，结合动态路由或带故障检测的备用路由，在当前路径故障时切换。
4. **电源冗余**：设备使用双电源，并尽量接入独立供电回路，配合 UPS 应对供电故障。

核心是消除单点故障，并具备故障检测和自动切换能力；同时避免备用设备、线路和电源共用同一个故障点。

#### 某老师反馈无法上网，完整排查思路？

我会按照“确认范围、检查连接、核对配置、分段测试、恢复验证”的顺序排查：

1. **确认范围**：询问故障时间和报错，是只有这台电脑无法上网，还是周围人也一样；是所有网站都打不开，还是只有某个网站；内网是否正常。
2. **检查连接**：查看网线、网卡和 Wi-Fi 状态，通过换网线、端口或同网络的正常设备做对照，定位电脑侧还是网络侧的问题。
3. **核对配置**：用 ipconfig /all 检查 IP、子网掩码、默认网关和 DNS，判断是否存在地址获取失败、配置错误或地址冲突。
4. **分段测试**：测试网关和已知可达的外网 IP，再用 nslookup 检查域名解析。网关不通优先检查本地接入；网关通但外网不通检查上游路由、出口及访问策略；IP 可达但解析失败则排查 DNS。结合实际连接测试判断，不能只凭 Ping 下结论。
5. **恢复验证**：若网络和解析正常，再检查校园网认证、浏览器、代理及防火墙策略。按定位结果修复后，让老师验证实际访问，记录原因与处理过程。

#### 简述 NAT 技术基本原理，列举典型应用场景。

NAT 是网络地址转换，由路由器或防火墙修改数据包的源或目的 IP 地址，并依据映射关系处理往返流量。常见的 NAPT 还会转换端口，使多台内网设备共享一个公网 IP，节省公网 IPv4 地址。

典型场景包括：

1. **家庭或企业共享上网**：将内网设备的源地址转换为公网地址后访问互联网。
2. **内网服务对外发布**：通过目的地址转换和端口映射，将公网指定端口的访问转发到内网 Web 等服务。
3. **云服务器访问外网**：没有直接配置公网 IP 的云服务器，通过 NAT 网关统一访问互联网。

#### 浏览器中点击一个链接，到页面返回内容，发生了什么？

以一次普通的网页导航为例：

1. 浏览器解析链接得到目标 URL，检查可用缓存；需要联网且没有可复用连接时，通过 DNS 缓存或查询获取目标地址。
2. 浏览器优先复用已有连接。需要新建连接时，HTTP/1.1、HTTP/2 通常基于 TCP，HTTPS 还要进行 TLS 握手，校验证书并协商加密参数；HTTP/3 使用基于 UDP 的 QUIC。
3. 浏览器发送 HTTP 请求，包含请求方法、路径、请求头，以及符合规则的 Cookie 等信息。
4. 请求可能经过 CDN、负载均衡和反向代理，由缓存或应用服务处理，必要时访问数据库，返回状态码、响应头和响应体；浏览器按响应处理重定向或缓存协商。
5. 对 HTML 响应，浏览器解析并构建 DOM、处理 CSS 和 JavaScript，继续加载所需资源，经样式计算、布局、绘制和合成显示页面。接收、解析和资源加载可以交错进行。

实际不一定每次都经过完整流程：缓存命中、连接复用，以及仅跳转页内锚点或由前端路由处理的链接，都可能省略部分步骤。

#### 域名解析的过程是什么？

以查询 www.example.com 的 IP 地址为例，常见流程是先利用浏览器、系统缓存及 hosts 等本机解析信息；未命中时，向配置的递归 DNS 解析器发起查询。

递归解析器先查自己的缓存。如果没有可用信息，则从根 DNS 服务器获取 .com 顶级域服务器的指引，再从 .com 服务器获取 example.com 权威 DNS 服务器的指引，最后查询权威服务器，获得 A（IPv4）或 AAAA（IPv6）等记录。如果遇到 CNAME 别名，则继续解析其目标名称。

解析器将结果返回客户端，并按 TTL 缓存记录。客户端到递归解析器通常采用递归查询，递归解析器向各级 DNS 服务器查询通常采用迭代方式；实际也可能配置转发器，或因缓存命中而跳过部分查询。

### Linux

#### Linux 部署 Web 服务无法访问，写至少四条 Linux 排查命令？

以 systemd 管理的 Nginx、HTTP 80 端口为例，我会依次检查服务状态、监听端口、本机访问、配置、日志和防火墙：

| 命令 | 排查目的 |
| --- | --- |
| `systemctl status nginx --no-pager` | 查看服务是否启动、是否启动失败 |
| `sudo ss -lntp` | 查看 TCP 监听端口、监听地址及对应进程 |
| `curl -v --max-time 5 http://127.0.0.1:80/` | 在服务器本机测试 HTTP 访问，观察连接和响应 |
| `sudo nginx -t` | 检查 Nginx 配置语法及相关文件是否可打开 |
| `sudo journalctl -u nginx -n 50 --no-pager` | 查看服务最近 50 条日志，排查启动等错误 |
| `sudo firewall-cmd --list-all-zones` | 使用 firewalld 时，查看各区域规则及网卡归属，检查实际生效区域是否允许 Web 访问 |

如果使用 UFW，则用 `sudo ufw status verbose` 查看防火墙规则。Nginx 请求错误还可用 `sudo tail -n 50 /var/log/nginx/error.log` 查看，日志路径以实际配置为准。

如果本机能访问、外部不能访问，重点检查是否只监听本机地址，以及防火墙、云安全组和端口映射；使用域名访问时，还需检查 DNS 和 HTTPS 配置。

### 数据结构

#### 线性探测哈希表，如何计算成功查找的平均查找长度？

先根据装填因子 α=n/m 确定表长，再按题目顺序计算哈希地址，冲突时依次检查后一个位置，到表尾后循环到表头。等概率成功查找的平均查找长度，是**查找各个已存关键字所需比较次数之和除以关键字个数**；第一次比较也计入。

### 数据库

#### MySQL 为什么使用 B+ 树？B 树和 B+ 树有什么区别？

这里主要指 InnoDB 的常规索引。B 树和 B+ 树都是多路平衡查找树。B 树的非叶节点和叶节点都可以保存关键字及其对应的数据记录或记录指针；B+ 树的非叶节点只保存导航用的键和子节点指针，索引记录集中在叶节点，叶节点之间按键顺序连接。

InnoDB 选择 B+ 树主要有两点：一是非叶节点不保存业务记录，同样大小的页能容纳更多导航项，分支更多、树通常更矮，有利于减少访问页的次数和磁盘 I/O；二是叶节点有序连接，范围查询和按索引顺序扫描时，定位起点后可以连续遍历，不必反复从根节点查找。

另外，InnoDB 聚簇索引的叶节点保存行记录，二级索引的叶节点保存索引列和主键值，需要其他列时可能通过主键回表。

#### 什么是聚簇索引、二级索引和覆盖索引？

以 InnoDB 为例：

- **聚簇索引**：叶节点保存行记录，一张表只有一个，通常以主键组织。如果没有主键，则选择第一个所有列都非空的唯一索引；仍没有时生成隐藏的行 ID 来组织聚簇索引。
- **二级索引**：聚簇索引以外的索引，叶节点保存索引列及主键值，一张表可以有多个。如果查询需要索引中没有的列，就要根据主键再访问聚簇索引，这称为回表。
- **覆盖索引**：某个索引已包含一次查询所需的全部列，通常无需为获取其他字段而回表。它描述索引对特定查询的覆盖关系，并不是与前两者并列的另一种存储结构。

例如，表有 id、name、age 三列，id 为主键，name 建有二级索引。查询 name 对应的 id、name 可以被该索引覆盖；查询 age 若使用该索引，则需要回表。EXPLAIN 中的 Using index 通常表示覆盖索引，Using index condition 表示索引条件下推，两者含义不同。

#### 事务有哪些隔离级别？

事务隔离级别用于控制并发事务之间的数据可见性，有四种：

1. **读未提交（Read Uncommitted）**：可以读到其他事务尚未提交的修改，可能出现脏读、不可重复读和幻读。
2. **读已提交（Read Committed）**：只读取其他事务已提交的修改，避免脏读，但同一事务中可能出现不可重复读和幻读。
3. **可重复读（Repeatable Read）**：避免脏读和不可重复读。按 SQL 标准的最低保证，仍可能出现幻读；InnoDB 的实现提供了更强的保护。
4. **串行化（Serializable）**：保证并发事务的执行结果等价于某种串行执行顺序，避免上述三种问题，但通常增加并发控制开销和等待。

InnoDB 默认使用可重复读：普通一致性读通常复用首次一致性读建立的快照，通过 MVCC 避免其他事务后续提交导致读结果变化；对锁定读和更新操作，则按查询条件使用记录锁、间隙锁或临键锁，保护相应记录与范围。快照读与当前读的规则不同，不能简单认为可重复读下所有查询都读取同一版本。

#### InnoDB 的 MVCC 是如何实现的？

MVCC 是多版本并发控制，InnoDB 主要通过**隐藏字段、Undo Log 和 Read View** 实现普通一致性读，减少读写之间的阻塞。

聚簇索引记录中的 DB_TRX_ID 标记最近修改它的事务，DB_ROLL_PTR 指向 Undo 记录。更新时保留重建旧版本所需的信息，从而可以沿版本链还原历史记录。

Read View 记录创建时的活跃读写事务集合、事务 ID 边界及创建者信息。读取时根据版本的事务 ID 判断可见性：自己的修改可见；快照建立前已提交的修改可见；当时仍活跃的其他事务及之后分配事务 ID 的事务，其修改不可见。若当前版本不可见，就沿 Undo 版本链继续寻找可见版本。

RC 下每次一致性读建立新的 Read View；RR 下通常在首次一致性读时建立，后续复用，因此能够重复读取相同快照。快照不是整表复制，也不意味着 UPDATE 或锁定读使用旧快照，写操作仍需要锁机制。

### Redis

#### Session 和 JWT 有什么区别？

通常比较的是服务端 Session 登录方案与自包含 JWT 登录方案。Session 将登录状态保存在服务端，客户端只携带随机 Session ID；请求时服务端根据 ID 查找会话。多实例部署时，可以用 Redis 共享 Session，并设置过期时间。

JWT 是一种令牌格式，常见登录方案将用户标识、过期时间等声明放入令牌并签名，由客户端携带；服务端验证签名和相关声明，可以不查询共享 Session 完成身份验证，便于多个服务独立校验。

Session 删除服务端会话即可撤销；纯无状态 JWT 在过期前较难单独撤销，仅删除客户端令牌并不能让已泄露的令牌失效，通常配合短有效期、刷新令牌管理或 Redis 黑名单，若每次查黑名单则又引入服务端状态。

另外，常见签名 JWT 的载荷只是编码，不是加密，不应存密码等敏感信息。Session ID 和 JWT 都可以通过 Cookie 携带，不能简单以 Cookie 和请求头区分两者。

#### JWT 如何防篡改、校验过期，以及处理密钥泄露？

1. **防篡改**：服务端使用密钥对令牌签名，请求到达时验证签名，内容被修改后验证会失败。使用成熟 JWT 库，限定允许的算法和可信密钥，拒绝非预期算法及无签名令牌；仅解码不能证明令牌可信。
2. **过期校验**：登录令牌要求包含 exp，并由服务端校验当前时间是否已达到过期时间；存在 nbf 时校验是否已经生效，还要按应用要求校验 iss、aud 等声明。可以设置小范围时钟偏差，不能依赖前端判断过期。
3. **密钥管理与泄露处理**：使用高强度密钥并妥善保管。HS256 使用共享密钥；RS256 使用私钥签名、公钥验签，公钥本身无需保密。签名密钥泄露后，立即生成新密钥，并让所有验签服务停止信任旧密钥，重新签发合法令牌，排查泄露原因；仅更换签发密钥但继续接受旧密钥并不能阻止伪造。

签名不等于加密，也不防止被盗令牌重放，应配合 HTTPS 和安全存储。Redis 黑名单可撤销特定令牌，但不能替代签名密钥泄露后的撤换，因为攻击者可以伪造新的令牌标识和过期时间。

### AI

#### 平时怎么使用 AI 开发需求？

我会先自己梳理需求，明确功能目标、输入输出、异常情况和验收标准，再把相关代码、技术栈及约束提供给 AI，让它先理解现有实现、梳理方案。

实现时会把需求拆成小任务，让 AI 分步辅助编写接口、重复代码和测试，每完成一步就检查代码差异并运行测试，确认没有影响原有功能。

遇到问题时，会提供报错日志、复现步骤和实际结果，让 AI 帮助分析，再通过调试验证。最后由我检查业务逻辑、权限校验和边界条件，完成联调，并让 AI 辅助整理文档和变更说明。核心是让 AI 提高开发效率，同时由自己理解代码、决定方案并验证结果。

#### 如何理解和使用 Rules、Skills、Agent、MCP 等 AI 开发能力？

我把它们理解为 AI 开发流程中的不同分工：

- **Rules**：可复用的开发约定，例如代码风格、目录规范和测试要求，按工具的作用范围和加载规则提供给 AI。
- **Skills**：针对具体任务封装的操作指南和资源，通常以 SKILL.md 描述何时使用、如何执行，也可以附带脚本和模板，适合沉淀重复流程。
- **Agent**：以模型为核心，结合上下文、工具和执行循环完成目标，能够读取代码、修改文件、运行测试，并根据结果继续调整。
- **MCP**：连接 AI 应用与外部工具、数据源的标准协议，例如接入文档检索、需求系统或数据库。它解决能力接入问题，本身不负责规划任务；本地文件和终端工具也不一定通过 MCP 提供。

使用时，我会先提供需求和相关上下文，用 Rules 固定项目约定，用 Skills 复用成熟流程，由 Agent 分步执行，按需通过 MCP 获取外部资料或调用服务，最后检查代码差异和测试结果。也需要理解 Prompt、工具调用和子 Agent 分工，但应按实际使用经历说明，不能把了解概念说成已经落地。

#### AI 编程还需要理解哪些配套能力？

除 Rules、Skills、Agent 和 MCP 外，我会重点理解以下能力：

- **Tool Calling / Function Calling**：向模型描述工具及参数，模型提出调用请求，由运行程序校验并执行，将结果返回模型，继续处理。MCP 负责标准化接入，Tool Calling 负责具体调用，两者并不等同。
- **Prompt 与上下文管理**：明确目标、约束和验收标准，提供相关代码、日志与文档。上下文窗口有限，需要按需检索、保留关键决策、压缩无关历史；Token 是模型处理文本等信息的计量单位，不等于字数。
- **Workflow 与 Agent Loop**：Workflow 以预设步骤组织任务，Agent 根据工具结果动态选择后续动作，两者可以结合，并设置结束条件及执行预算。
- **RAG 与记忆**：RAG 是检索相关资料后交给模型生成；持久记忆保存跨任务需要复用的信息，通常仍需加载或检索到当前上下文，两者都不等于训练模型。
- **Subagent**：把边界明确的任务交给子 Agent，主 Agent 汇总结果，适合独立分析和审查；并行修改需要协调冲突。
- **Hooks**：在工具调用前后、任务结束等事件上执行程序，例如格式化、检查和记录日志，具体事件取决于工具实现。
- **结构化输出与验证**：约束输出字段和格式，便于程序处理，但格式正确不代表内容正确，仍需参数校验、权限控制、实际测试与代码审查。

实际开发时，应将需求说明、相关上下文、工具执行和验证组织成完整流程，并控制操作权限、失败重试及成本，而不只关注模型生成了多少代码。

### 综合面试

#### 如果加入公司，你的个人优势是什么，能带来什么价值？

我的优势主要有三点。

第一是有比较完整的后端项目实践，从接口开发、数据库设计，到测试和部署都有实际参与，因此能够从功能实现和后续维护两个角度考虑问题。

第二是愿意通过实践验证问题。遇到不理解的原理或开发中的问题，我会通过编写小示例、查看日志和测试来验证自己的判断，弄清原因后再解决问题。

第三是主动学习新技术。我乐于接触新的技术和工具，会结合实际需求查阅文档、动手尝试，并把学习过程整理成技术记录，逐步应用到项目中。

如果有机会加入公司，我会先熟悉业务、现有代码和开发规范，从具体的接口开发、问题修复和测试任务入手，逐步独立承担模块。同时把重复操作和常见问题整理成脚本或文档，减少重复工作，方便后续维护和团队协作。
