### 计算机网络

#### 办公室 Wiki 卡顿，人员集中时明显，如何排查与优化？
我会先确认哪些人、哪些操作变慢，再对比同一台电脑使用 Wi-Fi 和网线访问的速度，初步判断是办公网络拥堵，还是服务器处理慢。

如果只有 Wi-Fi 慢，重点检查无线设备连接人数、信号干扰；如果有线也慢，就结合网络和服务器监控，检查出口带宽、服务器资源，以及数据库查询和请求排队情况。

找到瓶颈后，再调整无线网络、优化带宽使用，或优化数据库查询、增加缓存和服务器容量，最后对比高峰期的响应时间和错误率，确认优化有效。

#### 企业网络高可用设计常用的四种冗余手段？

可以从设备、链路、路由和电源四个方面回答：

1. **设备冗余**：关键交换机、路由器或防火墙部署两台，通过主备或集群方式，在一台故障时由另一台接替。
2. **链路冗余**：关键设备之间部署多条连接，通过链路聚合或备用链路，避免单条线路故障导致中断。
3. **路由冗余**：设计多条可达路径，结合动态路由或带故障检测的备用路由，在当前路径故障时切换。
4. **电源冗余**：设备使用双电源，并尽量接入独立供电回路，配合 UPS 应对供电故障。

核心是消除单点故障，并具备故障检测和自动切换能力；同时避免备用设备、线路和电源共用同一个故障点。

#### 某老师反馈无法上网，完整排查思路？

我会按照“确认范围、检查连接、核对配置、分段测试、恢复验证”的顺序排查：

1. **确认范围**：询问故障时间和报错，是只有这台电脑无法上网，还是周围人也一样；是所有网站都打不开，还是只有某个网站；内网是否正常。
2. **检查连接**：查看网线、网卡和 Wi-Fi 状态，通过换网线、端口或同网络的正常设备做对照，定位电脑侧还是网络侧的问题。
3. **核对配置**：用 ipconfig /all 检查 IP、子网掩码、默认网关和 DNS，判断是否存在地址获取失败、配置错误或地址冲突。
4. **分段测试**：测试网关和已知可达的外网 IP，再用 nslookup 检查域名解析。网关不通优先检查本地接入；网关通但外网不通检查上游路由、出口及访问策略；IP 可达但解析失败则排查 DNS。结合实际连接测试判断，不能只凭 Ping 下结论。
5. **恢复验证**：若网络和解析正常，再检查校园网认证、浏览器、代理及防火墙策略。按定位结果修复后，让老师验证实际访问，记录原因与处理过程。

#### 简述 NAT 技术基本原理，列举典型应用场景。

NAT 是网络地址转换，由路由器或防火墙修改数据包的源或目的 IP 地址，并依据映射关系处理往返流量。常见的 NAPT 还会转换端口，使多台内网设备共享一个公网 IP，节省公网 IPv4 地址。

典型场景包括：

1. **家庭或企业共享上网**：将内网设备的源地址转换为公网地址后访问互联网。
2. **内网服务对外发布**：通过目的地址转换和端口映射，将公网指定端口的访问转发到内网 Web 等服务。
3. **云服务器访问外网**：没有直接配置公网 IP 的云服务器，通过 NAT 网关统一访问互联网。

#### 浏览器中点击一个链接，到页面返回内容，发生了什么？

以一次普通的网页导航为例：

1. 浏览器解析链接得到目标 URL，检查可用缓存；需要联网且没有可复用连接时，通过 DNS 缓存或查询获取目标地址。
2. 浏览器优先复用已有连接。需要新建连接时，HTTP/1.1、HTTP/2 通常基于 TCP，HTTPS 还要进行 TLS 握手，校验证书并协商加密参数；HTTP/3 使用基于 UDP 的 QUIC。
3. 浏览器发送 HTTP 请求，包含请求方法、路径、请求头，以及符合规则的 Cookie 等信息。
4. 请求可能经过 CDN、负载均衡和反向代理，由缓存或应用服务处理，必要时访问数据库，返回状态码、响应头和响应体；浏览器按响应处理重定向或缓存协商。
5. 对 HTML 响应，浏览器解析并构建 DOM、处理 CSS 和 JavaScript，继续加载所需资源，经样式计算、布局、绘制和合成显示页面。接收、解析和资源加载可以交错进行。

实际不一定每次都经过完整流程：缓存命中、连接复用，以及仅跳转页内锚点或由前端路由处理的链接，都可能省略部分步骤。

#### 域名解析的过程是什么？

以查询 www.example.com 的 IP 地址为例，常见流程是先利用浏览器、系统缓存及 hosts 等本机解析信息；未命中时，向配置的递归 DNS 解析器发起查询。

递归解析器先查自己的缓存。如果没有可用信息，则从根 DNS 服务器获取 .com 顶级域服务器的指引，再从 .com 服务器获取 example.com 权威 DNS 服务器的指引，最后查询权威服务器，获得 A（IPv4）或 AAAA（IPv6）等记录。如果遇到 CNAME 别名，则继续解析其目标名称。

解析器将结果返回客户端，并按 TTL 缓存记录。客户端到递归解析器通常采用递归查询，递归解析器向各级 DNS 服务器查询通常采用迭代方式；实际也可能配置转发器，或因缓存命中而跳过部分查询。

#### 网络套接字 Socket 怎么用？

Socket 是操作系统提供的通信接口，程序通过它在网络上发送和接收数据。

TCP Socket 的基本流程：服务端先创建 Socket，绑定 IP 和端口并开始监听，再接收客户端连接；客户端创建 Socket 后，连接服务端的 IP 和端口。连接建立后，双方收发数据，结束后关闭。对应的常见调用是服务端 socket、bind、listen、accept，客户端 socket、connect，双方用 send、recv 收发数据。accept 返回一个用于当前连接的新 Socket，原来的 Socket 继续监听。

#### HTTPS 从建立连接到返回响应经历什么？TCP 和 TLS 分别做什么？

以需要新建连接的 HTTP/1.1 或 HTTP/2 为例：

浏览器先解析域名，得到服务器 IP，然后与服务器建立 TCP 连接，完成三次握手。接着进行 TLS 握手，协商版本和密码算法，验证服务器证书，通过密钥协商建立后续通信所需的密钥，并验证握手过程。之后再发送加密的 HTTP 请求，服务器处理后返回加密响应，浏览器解密并使用结果。

已有连接可以复用；HTTP/3 使用基于 UDP 的 QUIC，不直接套用上述 TCP 建连流程。

**TLS 1.3 完整握手的三个收发阶段**（以常见的服务端证书认证、无重试场景为例）：

1. **客户端 → 服务端：发起协商。** 发送 ClientHello，包含支持的版本、密码套件和密钥协商公开参数，让服务端选择方案并参与密钥协商。
2. **服务端 → 客户端：选择方案并证明身份。** 返回 ServerHello 和自身密钥协商公开参数，随后发送加密保护的证书、签名和 Finished，让客户端能够验证服务器身份及握手完整性，并派生相应密钥。
3. **客户端 → 服务端：验证并确认完成。** 客户端验证证书、签名和服务端 Finished，通过后发送自己的 Finished，让服务端确认客户端也正确完成握手，随后可发送加密的 HTTP 请求。

这里说的是三个收发阶段，不是只有三个报文，通常称为 1 RTT 握手；此前的 TCP 三次握手不计入其中。

#### 对称加密和非对称加密有什么区别？常见算法有哪些？

对称加密使用同一把密钥加密和解密，速度通常较快，适合加密大量数据，难点是双方如何安全共享密钥。常见算法有 AES、SM4、ChaCha20；DES、3DES 是传统算法，已不适合新系统使用。

非对称密码使用一对相关的公钥和私钥，公钥可以公开，私钥需要保密。在加密场景中，用接收方公钥加密，由接收方用私钥解密，速度通常比对称加密慢。常见加密算法有 RSA、SM2；ECC 是椭圆曲线密码技术的统称，其中不同方案分别用于加密、签名或密钥协商。数字签名是私钥签名、公钥验证，不宜简单理解为“私钥加密”。

实际常混合使用，例如 HTTPS 握手阶段通常利用非对称密码完成身份认证和密钥协商，之后使用对称加密保护业务数据。MD5、SHA-256、SM3 属于哈希算法，不是可解密还原的加密算法。

### Linux

#### Linux 部署 Web 服务无法访问，写至少四条 Linux 排查命令？

以 systemd 管理的 Nginx、HTTP 80 端口为例，我会依次检查服务状态、监听端口、本机访问、配置、日志和防火墙：

| 命令 | 排查目的 |
| --- | --- |
| `systemctl status nginx --no-pager` | 查看服务是否启动、是否启动失败 |
| `sudo ss -lntp` | 查看 TCP 监听端口、监听地址及对应进程 |
| `curl -v --max-time 5 http://127.0.0.1:80/` | 在服务器本机测试 HTTP 访问，观察连接和响应 |
| `sudo nginx -t` | 检查 Nginx 配置语法及相关文件是否可打开 |
| `sudo journalctl -u nginx -n 50 --no-pager` | 查看服务最近 50 条日志，排查启动等错误 |
| `sudo firewall-cmd --list-all-zones` | 使用 firewalld 时，查看各区域规则及网卡归属，检查实际生效区域是否允许 Web 访问 |

如果使用 UFW，则用 `sudo ufw status verbose` 查看防火墙规则。Nginx 请求错误还可用 `sudo tail -n 50 /var/log/nginx/error.log` 查看，日志路径以实际配置为准。

如果本机能访问、外部不能访问，重点检查是否只监听本机地址，以及防火墙、云安全组和端口映射；使用域名访问时，还需检查 DNS 和 HTTPS 配置。

如果是 Docker 部署的 API，再用 docker compose ps、docker compose logs --tail 100 backend 和 docker compose port nginx 80 检查容器状态、日志及对外端口；结合 docker inspect 核对网络和挂载，确认依赖服务是否可用。先 curl 本机实际 HTTP 入口，再查反向代理、监听地址、防火墙和云安全组。Ping 测试的是 IP 层可达性，不能用来检查 TCP 端口是否开放；端口可以用 ss、本机 curl 或 nc -vz 等工具检查。

### 数据结构

#### 线性探测哈希表，如何计算成功查找的平均查找长度？

先根据装填因子 α=n/m 确定表长，再按题目顺序计算哈希地址，冲突时依次检查后一个位置，到表尾后循环到表头。等概率成功查找的平均查找长度，是**查找各个已存关键字所需比较次数之和除以关键字个数**；第一次比较也计入。

### C++

#### 为什么 C++ 强调 RAII？它与 malloc/free 有什么区别？

RAII 就是让对象替我们管理资源：资源交给对象管理，在对象销毁时由析构函数自动释放。正常离开作用域、提前 return 或异常导致栈展开时，都可以自动清理，减少忘记释放的问题。

例如用 std::ifstream 管理文件，析构时关闭；用 std::lock_guard 管理互斥锁，构造时加锁、析构时解锁；用 std::vector 或 std::unique_ptr 管理动态内存。malloc/free 只负责分配和回收原始内存，不会自动调用对象的构造和析构，也不提供作用域清理；new/delete 会调用构造和析构，但手动配对仍可能出错，因此优先使用 RAII。

#### 指针和引用有什么区别？

指针是保存地址的对象，可以为空，也可以重新指向其他对象；引用可以理解为已有对象的别名，定义时需要绑定对象，之后不能改绑。引用本身不能改绑，不代表被引用的对象不能修改，例如 int& 可以修改原对象。通过引用操作对象时通常不需要显式解引用，通过指针则常用 * 或 ->。两者都可能因目标对象已经销毁而悬空，也都不自动拥有目标对象。

#### 函数参数什么时候传值、传引用或传指针？只读大对象怎么传？

int 等小且复制成本低的类型通常传值；只读大对象通常用 const T&，避免复制，并限制函数通过这个引用修改对象；需要修改调用者对象时可以用 T&；如果“没有对象”也是合法情况，可以用 T* 或 const T*，并检查空指针。

例如 void inspect(const BigObject& obj) 表示只读访问大对象，void update(BigObject& obj) 表示允许修改原对象。引用传参本身不要求复制对象，不能认为“不希望复制就只能用指针”。

#### 使用引用是否就不会悬空？

不是。悬空就是指针或引用还在，但它指向的对象已经不存在或原地址已经失效。返回普通局部对象的引用、对象 delete 后继续使用其引用，以及 vector 扩容后继续使用原元素引用，都可能出现悬空。引用通常要求绑定有效对象，但不会自动延长任意目标对象的生命周期。

#### const 在 C++ 中有什么作用？

const 用于表达只读约束。修饰普通对象时，不能直接修改该对象；修饰指针或引用所访问的对象时，限制通过该访问方式修改它；修饰非静态成员函数时，表示该函数不能通过 this 修改对象的普通数据成员，mutable 成员除外。const 不等于 static，也不保证一定是编译期常量，更不能保证对象一直存活。

#### 指向常量的指针和指针常量有什么区别？

看 const 限制的是所指对象还是指针本身，不要只背容易混淆的中文名称。

- const int* p 或 int const* p：不能通过 p 修改所指的 int，但 p 可以改为指向其他对象。

- int* const p：p 本身不能改指向，但可以通过 p 修改所指的 int。

- const int* const p：既不能改 p 的指向，也不能通过 p 修改所指的 int。

#### 函数返回 const 引用是否总是更安全？

不是。const 引用限制通过该引用修改对象，并不保证目标对象还活着。不能返回普通局部对象的 const 引用，因为函数结束后局部对象已销毁；返回对象成员或其他长期存在对象的引用，也要保证调用者使用期间该对象和被引用内容仍有效。需要返回新创建的结果时，通常优先按值返回，可以利用返回值优化或移动语义。

#### 局部对象和动态对象的生命周期有什么区别？返回局部对象地址有什么危险？

普通局部对象离开作用域时自动销毁；局部 static 对象是例外，不会在每次离开函数时销毁。new 创建的动态对象不会因为创建它的函数返回就自动销毁，需要通过 delete 或智能指针等资源管理方式清理。

返回普通局部对象的地址或引用后，调用者拿到的目标对象已经失效，继续访问属于未定义行为，可能看似正常，也可能崩溃或产生错误结果。动态内存如果长期不再需要却未释放，尤其失去管理途径时，会造成内存泄漏，但不一定立即崩溃；持续泄漏可能最终导致内存不足。

#### 拷贝和移动分别解决什么问题？移动一定更快吗？

拷贝用于根据原对象创建或更新另一个对象，具体是否复制底层资源取决于类型：vector 的拷贝通常复制元素，shared_ptr 的拷贝则共享所有权，裸指针的默认拷贝只复制地址。

移动让类型有机会把已有资源交给目标对象，避免不必要的复制，例如转移 unique_ptr 的所有权。std::move 本身只是进行类型转换，不负责搬运资源，也不保证一定调用移动操作。移动不一定比拷贝快，小对象可能差不多，类型也可能没有有效的移动实现。标准库对象移动后通常仍有效，但其具体内容可能未指定，不能一概认为原对象必然为空。

#### 运行时多态为什么需要虚函数？

通过基类指针或引用调用虚函数时，C++ 会根据实际对象的类型选择实现，例如基类指针指向派生类对象时，可以调用派生类重写的函数。如果对应函数不是虚函数，这类调用通常按指针或引用的静态类型选择实现。

这里说的是运行时多态；函数重载、模板等也可以实现编译期多态，并不是所有多态都依赖虚函数。通过基类指针删除派生类对象时，基类通常需要虚析构函数，保证正确完成销毁。

#### vector、list 和 map 如何选型？

- vector 是动态数组，元素连续存储，支持按下标快速访问，尾部追加摊还 O(1)，中间插入和删除通常 O(n)，适合多数顺序存储和遍历场景，可以优先考虑。

- list 通常是双向链表，不支持下标随机访问；已经拿到目标位置的迭代器时，插入和删除是 O(1)，但查找位置通常 O(n)，适合确实需要稳定迭代器或频繁在已知位置修改的场景。

- map 保存按键排序的键值对，键唯一，值可以重复，查找、插入、删除通常 O(log n)，适合按键查询及有序遍历，常见实现是红黑树。

选型还要考虑内存开销、缓存局部性和迭代器失效，不能只凭“插入多就用 list”判断。

#### 智能指针能解决哪些问题，不能解决哪些问题？

智能指针主要管理动态资源的所有权和释放时机，减少忘记 delete、异常路径漏释放等问题。unique_ptr 表示独占所有权，可以移动但不能拷贝；shared_ptr 表示共享所有权，最后一个所有者释放时清理资源；weak_ptr 用于不增加共享所有者数量的观察关系，常用于打破循环引用。

智能指针不能自动解决数组越界、通过裸指针访问已释放对象、对象内部的数据竞争等问题。shared_ptr 之间形成循环所有权仍可能泄漏，应合理使用 weak_ptr；也不能用多个独立的 shared_ptr 分别接管同一裸指针，否则可能重复释放。

#### C++ 程序内存持续增长或间歇性崩溃，如何排查？

内存增长时，先对比固定负载下的内存曲线，区分业务数据或缓存增长、容器保留容量、分配器保留内存和真正泄漏，再用 LeakSanitizer 或支持的平台上的 Valgrind 等工具定位未释放的分配点，检查所有权、异常路径和 shared_ptr 循环引用。

间歇性崩溃时，保留日志、调试符号和 core 文件，用 GDB 查看崩溃线程的调用栈，尝试缩小复现条件。用 AddressSanitizer 检查越界、释放后使用、重复释放等问题；怀疑多线程竞争时，单独用 ThreadSanitizer 辅助检查。修复后针对原触发条件反复验证，不能只凭程序暂时不崩溃判断已经解决。

#### 指针变量与动态内存有什么区别？哪些情况需要 delete？

指针是保存地址的变量，可以指向已有局部对象、数组，也可以指向动态分配的对象，声明指针本身不意味着为它指向的对象分配内存。例如 int x = 10; int* p = &x; 不需要也不能 delete p。

使用 new 创建并由自己负责管理的对象，应按所有权约定释放；new 对应 delete，new[] 对应 delete[]，malloc 对应 free，不能混用。delete 清理的是动态对象及其存储，原指针变量仍然存在，应避免继续使用悬空地址。现代 C++ 优先用 vector、string、unique_ptr 等管理资源；使用非拥有型指针时，不应擅自释放别人的对象。

### 数据库

#### MySQL 为什么使用 B+ 树？B 树和 B+ 树有什么区别？

这里主要指 InnoDB 的常规索引。B 树和 B+ 树都是多路平衡查找树。B 树的非叶节点和叶节点都可以保存关键字及其对应的数据记录或记录指针；B+ 树的非叶节点只保存导航用的键和子节点指针，索引记录集中在叶节点，叶节点之间按键顺序连接。

InnoDB 选择 B+ 树主要有两点：一是非叶节点不保存业务记录，同样大小的页能容纳更多导航项，分支更多、树通常更矮，有利于减少访问页的次数和磁盘 I/O；二是叶节点有序连接，范围查询和按索引顺序扫描时，定位起点后可以连续遍历，不必反复从根节点查找。

另外，InnoDB 聚簇索引的叶节点保存行记录，二级索引的叶节点保存索引列和主键值，需要其他列时可能通过主键回表。

#### 什么是聚簇索引、二级索引和覆盖索引？

以 InnoDB 为例：

- **聚簇索引**：叶节点保存行记录，一张表只有一个，通常以主键组织。如果没有主键，则选择第一个所有列都非空的唯一索引；仍没有时生成隐藏的行 ID 来组织聚簇索引。
- **二级索引**：聚簇索引以外的索引，叶节点保存索引列及主键值，一张表可以有多个。如果查询需要索引中没有的列，就要根据主键再访问聚簇索引，这称为回表。
- **覆盖索引**：某个索引已包含一次查询所需的全部列，通常无需为获取其他字段而回表。它描述索引对特定查询的覆盖关系，并不是与前两者并列的另一种存储结构。

例如，表有 id、name、age 三列，id 为主键，name 建有二级索引。查询 name 对应的 id、name 可以被该索引覆盖；查询 age 若使用该索引，则需要回表。EXPLAIN 中的 Using index 通常表示覆盖索引，Using index condition 表示索引条件下推，两者含义不同。

#### 事务有哪些隔离级别？

事务隔离级别用于控制并发事务之间的数据可见性，有四种：

1. **读未提交（Read Uncommitted）**：可以读到其他事务尚未提交的修改，可能出现脏读、不可重复读和幻读。
2. **读已提交（Read Committed）**：只读取其他事务已提交的修改，避免脏读，但同一事务中可能出现不可重复读和幻读。
3. **可重复读（Repeatable Read）**：避免脏读和不可重复读。按 SQL 标准的最低保证，仍可能出现幻读；InnoDB 的实现提供了更强的保护。
4. **串行化（Serializable）**：保证并发事务的执行结果等价于某种串行执行顺序，避免上述三种问题，但通常增加并发控制开销和等待。

InnoDB 默认使用可重复读：普通一致性读通常复用首次一致性读建立的快照，通过 MVCC 避免其他事务后续提交导致读结果变化；对锁定读和更新操作，则按查询条件使用记录锁、间隙锁或临键锁，保护相应记录与范围。快照读与当前读的规则不同，不能简单认为可重复读下所有查询都读取同一版本。

#### InnoDB 的 MVCC 是如何实现的？

MVCC 是多版本并发控制，InnoDB 主要通过**隐藏字段、Undo Log 和 Read View** 实现普通一致性读，减少读写之间的阻塞。

聚簇索引记录中的 DB_TRX_ID 标记最近修改它的事务，DB_ROLL_PTR 指向 Undo 记录。更新时保留重建旧版本所需的信息，从而可以沿版本链还原历史记录。

Read View 记录创建时的活跃读写事务集合、事务 ID 边界及创建者信息。读取时根据版本的事务 ID 判断可见性：自己的修改可见；快照建立前已提交的修改可见；当时仍活跃的其他事务及之后分配事务 ID 的事务，其修改不可见。若当前版本不可见，就沿 Undo 版本链继续寻找可见版本。

RC 下每次一致性读建立新的 Read View；RR 下通常在首次一致性读时建立，后续复用，因此能够重复读取相同快照。快照不是整表复制，也不意味着 UPDATE 或锁定读使用旧快照，写操作仍需要锁机制。

#### SQL 占位符有什么作用？批量 INSERT 时每条记录的字段不一致如何处理？

占位符用于参数化查询，把 SQL 结构与数据值分开，由驱动绑定参数，避免手动拼接数据带来的 SQL 注入风险。常见形式有 ?、%s、:name，具体取决于驱动；普通参数占位符不能代替表名、列名或 SQL 关键字。

每条记录提供的字段不同，我会先把字段相同的记录分组，再分别批量插入。例如，都有姓名和年龄的记录放一组，有姓名和城市的记录放另一组。

动态处理时，程序遍历每条记录，把它包含的字段按固定顺序排列，作为分组依据。然后根据每组的字段动态生成 INSERT 的列名列表和对应数量的占位符，再按相同顺序提取每条记录的值，交给驱动批量执行。比如字段是 name、age，就生成 INSERT INTO users (name, age) VALUES (%s, %s)，数据值另外通过参数传入。

列名只允许使用事先规定好的字段；没有提供的字段由数据库按默认值等规则处理，必填且没有默认值的字段需要提前检查。如果要求这批数据要么全部成功、要么全部失败，就把各组插入放在同一个事务中。

#### 一条 SELECT 从客户端发出，到读取数据并返回结果，经历了什么？

以 MySQL 8.0 及以上版本、InnoDB 的普通 SELECT 为例：

客户端先建立或复用数据库连接，建立连接时验证身份，再把 SQL 发给 MySQL。MySQL 解析语句，检查语法、表和字段，并校验查询权限；优化器再根据索引和统计信息，选择预计成本较低的执行计划。

执行器按计划调用 InnoDB 读取数据：可以通过 B+ 树索引定位记录，也可能扫描整张表。访问索引页、数据页时，先查内存中的 Buffer Pool；没有对应页时，再从表空间文件读取到内存。主键索引的叶节点保存行数据；使用二级索引且缺少所需字段时，还要根据主键回表。普通一致性读还需要按 MVCC 规则获取当前事务可见的版本。

查询按计划完成过滤、排序或聚合等必要操作，再通过连接把结果返回客户端。数据页在内存中命中时，不需要为读取这些页再次访问磁盘；可以流式执行的查询，也不必等所有结果收集完才开始返回。

#### 说说 MySQL 客户端/服务器协议。

MySQL 客户端/服务器协议是 MySQL 数据库系统中用于客户端与服务器之间通信的一套专有网络协议。

MySQL 客户端/服务器协议规定客户端和数据库如何建立连接、验证身份、发送命令和返回结果。这里主要指经典协议，它是应用层协议，网络连接通常基于 TCP，默认端口为 3306，本机也可以通过 Unix Socket 等方式连接。

通信主要分两个阶段：连接阶段由服务端先发送握手信息，双方协商支持的功能、完成身份认证，也可以协商 TLS 加密；命令阶段由客户端发送 SQL 等命令，服务端返回查询结果集、成功信息或错误信息。普通查询通常通过 COM_QUERY 发送 SQL 文本；使用服务器端预处理时，则通过准备、执行等命令分别传递 SQL 模板和参数。

同一连接通常按“发送命令、接收完整响应、再发送下一条命令”的顺序交互，这种请求响应方式常被称为半双工，但底层 TCP 本身是全双工。驱动负责按协议封装和解析数据包；普通 MySQL 协议包有 4 字节包头，其中 3 字节表示负载长度，1 字节表示包序号。

#### 数据库记录持续增加、按一列或多列查询越来越慢，如何优化？

我会先定位具体慢 SQL，用 EXPLAIN 查看执行计划，检查是否扫描过多记录、是否使用了合适的索引，以及是否有额外排序。根据常见的筛选条件、排序和分页方式，建立合适的单列或联合索引，避免对索引列做不利于索引查找的运算或隐式类型转换。

只查询必要列、控制返回行数，可以减少读取和传输开销，但不能代替索引设计。深分页可以考虑基于上次记录的主键或排序键继续查询。最后对比扫描行数和耗时，并关注新增索引对持续写入和存储空间的影响；数据归档、分区或拆分应在确认瓶颈后按需考虑。

#### 联合索引的列顺序怎么选？什么是最左前缀原则？

联合索引按建索引时的列顺序组织。索引 (a, b, c) 通常能支持按 a、(a, b)、(a, b, c) 从左向右定位；只查 b 或 c，通常不能按普通的最左前缀方式高效定位，但不能绝对说完全不会使用该索引。

列顺序应结合实际查询：经常单独作为查询条件的列适合放在前面；等值筛选列通常放在范围筛选列前面，还要兼顾排序和分组。例如经常按 user_id、status 等值筛选，再按 created_at 查时间范围，可以考虑 (user_id, status, created_at)。SQL 中 WHERE 条件的书写顺序不决定索引列顺序，不能机械地认为区分度最高的列永远放最前；最终用 EXPLAIN 和实际耗时验证。

#### 按用户和创建时间查询任务，如何设计索引？索引有什么成本？

如果常见查询是 WHERE user_id = ?，再按 created_at 排序或查时间范围，可以考虑 (user_id, created_at) 联合索引：先定位用户，再在该用户的数据中按时间查找。需要稳定分页时加入主键作为同一时间下的排序依据，再用 EXPLAIN 和真实数据验证索引及排序效果。

索引并非越多越好：会占用磁盘和缓存，插入、删除以及修改索引列时需要维护索引结构，增加写入成本；重复或很少使用的索引应结合实际负载评估。只写了单列索引，并不等于已经有了适合筛选加排序的联合索引。

### Redis

#### Session 和 JWT 有什么区别？

通常比较的是服务端 Session 登录方案与自包含 JWT 登录方案。Session 将登录状态保存在服务端，客户端只携带随机 Session ID；请求时服务端根据 ID 查找会话。多实例部署时，可以用 Redis 共享 Session，并设置过期时间。

JWT 是一种令牌格式，常见登录方案将用户标识、过期时间等声明放入令牌并签名，由客户端携带；服务端验证签名和相关声明，可以不查询共享 Session 完成身份验证，便于多个服务独立校验。

Session 删除服务端会话即可撤销；纯无状态 JWT 在过期前较难单独撤销，仅删除客户端令牌并不能让已泄露的令牌失效，通常配合短有效期、刷新令牌管理或 Redis 黑名单，若每次查黑名单则又引入服务端状态。

另外，常见签名 JWT 的载荷只是编码，不是加密，不应存密码等敏感信息。Session ID 和 JWT 都可以通过 Cookie 携带，不能简单以 Cookie 和请求头区分两者。

#### JWT 如何防篡改、校验过期，以及处理密钥泄露？

1. **防篡改**：服务端使用密钥对令牌签名，请求到达时验证签名，内容被修改后验证会失败。使用成熟 JWT 库，限定允许的算法和可信密钥，拒绝非预期算法及无签名令牌；仅解码不能证明令牌可信。
2. **过期校验**：登录令牌要求包含 exp，并由服务端校验当前时间是否已达到过期时间；存在 nbf 时校验是否已经生效，还要按应用要求校验 iss、aud 等声明。可以设置小范围时钟偏差，不能依赖前端判断过期。
3. **密钥管理与泄露处理**：使用高强度密钥并妥善保管。HS256 使用共享密钥；RS256 使用私钥签名、公钥验签，公钥本身无需保密。签名密钥泄露后，立即生成新密钥，并让所有验签服务停止信任旧密钥，重新签发合法令牌，排查泄露原因；仅更换签发密钥但继续接受旧密钥并不能阻止伪造。

签名不等于加密，也不防止被盗令牌重放，应配合 HTTPS 和安全存储。Redis 黑名单可撤销特定令牌，但不能替代签名密钥泄露后的撤换，因为攻击者可以伪造新的令牌标识和过期时间。

#### 布隆过滤器是什么，有什么应用？

布隆过滤器是一种节省内存、快速判断某个元素是否加入过集合的数据结构。它用位数组和多个哈希函数，把每个元素对应的几个位置标记为 1；查询时，只要有一个对应位置为 0，就说明该元素一定没有加入过，如果全为 1，则只能说明可能存在，因为其他元素也可能把这些位置标记为 1。因此它可能误报存在，但标准布隆过滤器不会把已经加入的元素判断为不存在；也不保存原始数据，不能直接删除元素。

典型应用是防止缓存穿透：先把数据库中有效的 ID 加入过滤器，请求到来时，如果判断一定不存在，就直接返回；如果可能存在，再正常查缓存和数据库，减少无效请求对数据库的访问。新增数据时需要及时维护过滤器，避免遗漏有效 ID。它也可以用于爬虫 URL 去重、推荐内容去重等允许一定误判的场景，以及数据库读取磁盘文件前的存在性预检查。

#### Redis 哨兵的基本原理是什么？

我项目中使用的是单实例 Redis，没有实际部署过哨兵。哨兵是基于主从复制实现高可用的一组独立进程，主要负责监控、故障通知、自动故障转移，并向客户端提供当前主库地址。

哨兵定期探测 Redis 节点。某个哨兵判断主库不可达时，先标记为主观下线；达到配置的 quorum 数量的哨兵确认后，标记为客观下线。再通过投票获得多数哨兵授权，由领头哨兵选择合适的从库提升为新主库，让其他从库复制新主库。支持哨兵的客户端重新发现主库地址并连接；旧主库恢复后会被重新配置为从库。quorum 是故障确认门槛，故障转移还需要多数授权。

通常部署至少 3 个哨兵，分布在不同故障域，避免哨兵自身成为单点。主从复制通常是异步的，因此哨兵可以提高可用性，但不能保证切换期间零数据丢失。

### AI

#### 平时怎么使用 AI 开发需求？

我会先自己梳理需求，明确功能目标、输入输出、异常情况和验收标准，再把相关代码、技术栈及约束提供给 AI，让它先理解现有实现、梳理方案。

实现时会把需求拆成小任务，让 AI 分步辅助编写接口、重复代码和测试，每完成一步就检查代码差异并运行测试，确认没有影响原有功能。

遇到问题时，会提供报错日志、复现步骤和实际结果，让 AI 帮助分析，再通过调试验证。最后由我检查业务逻辑、权限校验和边界条件，完成联调，并让 AI 辅助整理文档和变更说明。核心是让 AI 提高开发效率，同时由自己理解代码、决定方案并验证结果。

#### 如何理解和使用 Rules、Skills、Agent、MCP 等 AI 开发能力？

我把它们理解为 AI 开发流程中的不同分工：

- **Rules**：可复用的开发约定，例如代码风格、目录规范和测试要求，按工具的作用范围和加载规则提供给 AI。
- **Skills**：针对具体任务封装的操作指南和资源，通常以 SKILL.md 描述何时使用、如何执行，也可以附带脚本和模板，适合沉淀重复流程。
- **Agent**：以模型为核心，结合上下文、工具和执行循环完成目标，能够读取代码、修改文件、运行测试，并根据结果继续调整。
- **MCP**：连接 AI 应用与外部工具、数据源的标准协议，例如接入文档检索、需求系统或数据库。它解决能力接入问题，本身不负责规划任务；本地文件和终端工具也不一定通过 MCP 提供。

使用时，我会先提供需求和相关上下文，用 Rules 固定项目约定，用 Skills 复用成熟流程，由 Agent 分步执行，按需通过 MCP 获取外部资料或调用服务，最后检查代码差异和测试结果。也需要理解 Prompt、工具调用和子 Agent 分工，但应按实际使用经历说明，不能把了解概念说成已经落地。

#### AI 编程还需要理解哪些配套能力？

除 Rules、Skills、Agent 和 MCP 外，我会重点理解以下能力：

- **Tool Calling / Function Calling**：向模型描述工具及参数，模型提出调用请求，由运行程序校验并执行，将结果返回模型，继续处理。MCP 负责标准化接入，Tool Calling 负责具体调用，两者并不等同。
- **Prompt 与上下文管理**：明确目标、约束和验收标准，提供相关代码、日志与文档。上下文窗口有限，需要按需检索、保留关键决策、压缩无关历史；Token 是模型处理文本等信息的计量单位，不等于字数。
- **Workflow 与 Agent Loop**：Workflow 以预设步骤组织任务，Agent 根据工具结果动态选择后续动作，两者可以结合，并设置结束条件及执行预算。
- **RAG 与记忆**：RAG 是检索相关资料后交给模型生成；持久记忆保存跨任务需要复用的信息，通常仍需加载或检索到当前上下文，两者都不等于训练模型。
- **Subagent**：把边界明确的任务交给子 Agent，主 Agent 汇总结果，适合独立分析和审查；并行修改需要协调冲突。
- **Hooks**：在工具调用前后、任务结束等事件上执行程序，例如格式化、检查和记录日志，具体事件取决于工具实现。
- **结构化输出与验证**：约束输出字段和格式，便于程序处理，但格式正确不代表内容正确，仍需参数校验、权限控制、实际测试与代码审查。

实际开发时，应将需求说明、相关上下文、工具执行和验证组织成完整流程，并控制操作权限、失败重试及成本，而不只关注模型生成了多少代码。

#### 最近关注哪些新技术？怎么使用的？

我最近比较关注 AI Agent 在软件开发中的应用，主要是让 AI 结合项目代码，调用工具完成代码修改、运行测试等多个步骤。

实际使用比较多，除了简历上的项目，我还用 AI 开发过几个个人项目，项目代码主要由 AI 编写。使用时，我会先说明要实现的功能和使用的技术栈，让它分步骤实现；遇到问题，再结合报错日志和实际运行结果继续调整。

对我来说，它的价值是能更快地把想法做成可运行的项目。同时，我也在加强对关键代码和实现原理的理解，结合测试验证功能和边界情况，避免只停留在“代码能运行”的层面。

#### 如何验证 AI 生成的代码满足需求？只手工用一下够吗？

先把需求变成明确的验收条件，再让 AI 实现并逐项检查。除正常操作外，还要覆盖错误输入、权限、依赖失败、并发与资源限制等边界；手工操作可以确认体验，自动化测试则用于重复验证接口行为和防止修改后退化。

例如蛋白质项目已有针对非法输入、推理异常、忙时 503、模型加载和释放的模拟模型测试；图片项目已有登录、上传、用户隔离、限流及健康检查测试。应能解释每类测试的输入、期望状态码和断言，并展示实际执行结果。测试文件存在不代表已经运行通过，模拟模型测试也不能证明真实模型预测准确；还应单独验证真实权重和实际依赖。

### 软件工程

#### 说说常见的设计模式。

设计模式是解决常见软件设计问题的经验，主要分为创建型、结构型和行为型。我了解的常见模式有：

- **单例模式（创建型）**：在约定范围内只保留某个类的一个实例，并提供统一访问入口，例如共享的配置管理对象；需要注意并发访问和生命周期管理。
- **工厂模式（创建型）**：把对象创建过程封装起来，调用方通过统一接口使用对象，减少对具体类的依赖，例如根据文件类型创建不同的解析器。
- **适配器模式（结构型）**：把已有接口转换成调用方需要的接口，例如把不同厂商的短信接口统一成相同的调用方式。
- **装饰器模式（结构型）**：通过包装原对象来叠加功能，例如在原有读取功能外增加缓存或日志。
- **策略模式（行为型）**：把不同算法或处理方式分别封装起来，按需要选择，例如选择按重量或按距离计算运费。
- **观察者模式（行为型）**：一个对象状态变化时通知订阅它的多个对象，例如订单状态变化后通知消息和统计模块。

实际使用时要根据问题选择，避免为了套用模式增加不必要的复杂度；了解模式原理也不等于已经在项目中使用过。

#### 用户修改订单 ID 就能访问他人订单，如何防止越权？

这是水平越权，也属于对象级授权缺失。对于普通用户只能查询自己订单的场景，后端应先验证登录身份，从可信 Session 或已验证的 JWT 中取得当前用户 ID，再按订单 ID 和当前用户 ID 一起查询，或查询后检查订单归属，不能直接信任前端传入的用户 ID。无权限时返回 403，或按统一策略返回 404，不返回订单内容。

查询、修改、删除、下载等每个涉及具体资源的接口都要做后端权限校验；存在管理员、共享订单或多租户时，要进一步按角色、授权关系和租户范围判断。隐藏前端按钮、把 ID 换成 UUID 都不能代替权限检查。测试时用两个不同用户，验证本人访问成功、修改 ID 后访问他人资源被拒绝。

### 操作系统

#### 进程、线程和协程有什么区别？I/O 密集和 CPU 密集任务怎么选？

进程是资源分配和隔离的重要单位，通常有独立地址空间；线程是操作系统调度执行的单位，同一进程的线程共享地址空间；协程是在用户态组织的执行任务，async/await 场景通常在等待 I/O 时主动让出执行机会。

大量网络等待适合异步协程；阻塞式 I/O 库可放在线程池中；纯 Python 的 CPU 密集计算在常规带 GIL 的 CPython 下，通常考虑多进程。PyTorch 等底层库可能释放 GIL 或使用 GPU，不能机械套用；推理服务要结合线程池、独立模型进程和内存显存限制。FastAPI 的普通 def 路由在线程池运行，改成 async def 不会自动让重计算并行。

补充进程与线程：进程通常有独立地址空间，线程共享同一进程的代码、全局数据和堆，但各自有栈和寄存器执行状态。多进程适合需要较强隔离、独立重启或独立资源边界的任务；多线程适合进程内协作及共享数据的并发处理。C++ 中多线程也可以利用多核执行 CPU 密集任务，不能把 Python 带 GIL 场景的经验当成通用规则。线程正常结束不会让其他线程一起结束，但越界等致命错误可能使整个进程退出。

#### 常见的进程间通信方式有哪些？

常见方式包括管道、命名管道、消息队列、共享内存、信号和 Socket。管道用于传递字节流；消息队列按消息传递数据；共享内存让多个进程访问同一块内存，减少复制，但通常需要额外同步；信号主要用于事件通知；Socket 可用于本机不同进程或跨机器通信。信号量主要用于进程间同步和互斥，也常一起介绍。进程池是管理和复用工作进程的方式，不是独立的通信机制。

#### 僵尸进程是怎么产生的，如何避免？

子进程已经退出，但父进程尚未用 wait、waitpid 等接口读取其退出状态时，系统会保留必要的进程记录，形成僵尸进程。关键是没有回收退出状态，不是父进程还活着就一定产生僵尸。

父进程应及时等待并回收子进程；需要同时处理其他工作时，可以结合 SIGCHLD 通知，循环调用 waitpid(-1, &status, WNOHANG) 回收已退出的子进程。僵尸已经不再执行，不能靠给它发送 kill -9 解决；应修复父进程的回收逻辑。

### Docker

#### 镜像、容器和数据卷有什么区别？重启后数据丢失怎么排查？

镜像是用于创建容器的只读模板；容器是基于镜像创建的实例，有自己的可写层和运行进程；数据卷或绑定挂载用于把需要持久保存的数据放在容器可写层之外。

先分清是重启同一个容器，还是删除后重建。普通重启通常不会清空容器可写层；若数据丢失，要检查实际写入路径是否落在挂载目录、数据卷是否换了、Compose 项目名是否变化、是否误删数据卷，以及启动脚本是否重置数据。用 docker inspect 查看 Mounts，用 docker volume inspect 核对卷。图片项目中 MySQL、Garage 元数据和图片数据、Redis 都有命名卷，持久化之外仍需要备份。

#### Dockerfile 怎么写？常见指令分别做什么？

Dockerfile 描述镜像的构建步骤。FROM 选择基础镜像，WORKDIR 设置工作目录，COPY 复制依赖文件和源码，RUN 在构建时安装依赖或执行命令，ENV 设置环境变量，CMD 或 ENTRYPOINT 指定容器启动时运行的程序。EXPOSE 只是声明端口，不等于向宿主机发布端口，端口映射要通过 Compose 的 ports 或 docker run -p 设置。

图床后端先复制 requirements.txt 并安装依赖，再复制源码，方便复用依赖安装缓存；启动命令先执行 Alembic 迁移，再用 Uvicorn 在 0.0.0.0:8000 提供服务。修改打包进镜像的源码后，需要重新构建并更新容器。

#### Docker Compose 中的容器如何通信？和数据卷有什么区别？

同一 Compose 项目的服务默认加入同一个网络，通过服务名和容器内部端口访问。例如 Nginx 通过 http://backend:8000 访问后端，后端通过 mysql:3306、redis:6379 和 http://garage:3900 访问依赖。Docker 的内部 DNS 把服务名解析到相应容器地址，通常不需要固定容器 IP。

普通独立网络容器中的 127.0.0.1 指向自身，不能拿它访问其他容器。宿主机通过发布端口访问容器，例如宿主机 8080 映射到 Nginx 容器 80；容器间通常使用内部端口。数据卷解决文件持久化或共享问题，不负责建立服务间网络通信。

### 项目相关

#### 蛋白质预测项目中，一次真实请求从提交到返回结果的流程是什么？

当前版本由网页提交 sequence 和 mutations，例如 F88Y 表示第 88 位由 F 变为 Y。FastAPI 用 Pydantic 和自定义校验检查字段类型、序列字符、突变位置及原始氨基酸，再取得启动时已经加载好的 ModelService。

路由尝试获取推理锁，成功后生成突变序列，分别提取原序列与突变序列的 ESM 特征，交给预测网络得到 ΔΔG。最后检查结果是有限数值，返回 ddg、length、mutation、mutation_count 的 JSON，由网页展示。输入错误返回 400，忙时返回 503，推理失败返回 500。

#### 蛋白质预测模型如何处理序列和突变特征？

先根据原序列和突变信息生成突变序列，用 ESM-2 分别提取两条序列每个位置的 1280 维特征，计算原序列特征减去突变序列特征的差异。

差异特征进入卷积和 Transformer 两条通路，各自处理后做平均池化、最大池化，分别得到 256 维向量。两路经过门控加权后仍拼接为 512 维，再拼接由氨基酸理化差异特征映射出的 32 维向量，形成 544 维输入，最终通过全连接层回归输出一个 ΔΔG。接口支持多点输入，并不等于已经验证了多点预测效果。

#### 预测接口如何处理非法输入、推理失败和超长请求？

当前代码在后端校验氨基酸字符、突变格式、位置是否越界、原始残基是否匹配、位置是否重复，以及最多 10 个突变；非法输入统一返回 400，不会进入模型。推理异常或输出 NaN、无穷值时记录内部日志，对外返回通用的 500；已有推理正在执行时返回 503 和 Retry-After。

当前公开版本没有明确的序列长度上限或单任务执行超时。进一步完善时，应根据模型支持范围和硬件限制设置输入长度、请求体大小、执行时间及排队容量，避免超长请求耗尽资源；不能只依赖前端校验。

#### 多个用户提交耗时较长的预测任务，如何设计提交、执行和查询？

长任务就是不能让用户一直保持 HTTP 连接等待的耗时操作。当前项目是同步预测，单进程用非阻塞锁限制同一时刻只有一次推理，忙时返回 503；不是因为只有一个进程就会自动拒绝其他请求。

如果扩展，我会把接收请求和执行预测分开：接口校验并保存任务后，返回 202 和 task_id；任务进入队列，由独立的模型工作进程处理，状态依次记录为等待、运行、成功或失败。前端通过任务 ID 查询状态和结果。再补充队列限额、超时、有限重试、防重复执行和服务重启后的恢复，模型进程数量按内存或显存容量决定。这是扩展方案，当前仓库尚未实现。

#### 如何设计预测任务、输入、模型版本和结果的数据库表？

当前预测项目没有任务数据库。若扩展，可用 models 表保存不可变的模型版本、权重摘要和预处理配置；tasks 表保存任务 ID、用户 ID（引入用户体系后）、模型版本、输入或输入文件位置、输入摘要、状态、错误码及创建和开始结束时间；结果较小时可以放在任务表，较大或一对多时再拆 results 表，通过 task_id 关联。

查询任务详情按主键；按用户查询历史任务时考虑 (user_id, created_at) 联合索引。输入摘要可辅助识别重复请求，但相同输入在不同模型版本下不能直接视为同一结果。应用版本号不等于模型权重版本，权重或预处理变化应能追溯。

#### 批量推理的 padding、mask 与离线任务断点恢复有什么区别？

padding 是把一批不同长度的序列补到相同长度，方便组成张量；mask 告诉注意力或池化哪些位置是补齐的，不应作为有效残基处理。这解决的是批输入如何计算的问题。

断点恢复解决的是任务中断后如何继续：给每条输入稳定的标识，持久化处理状态、结果和模型版本，重新启动时跳过已完成项，只重试未完成或失败项，并防止重复写入。当前公开仓库能看到 lengths 和 mask 的处理，但没有看到独立的离线批处理或断点恢复流程，不能用“补零对齐”解释简历中的可靠性能力；其他代码若实现了，应准备对应证据。

#### 同一蛋白质或高度相似序列同时出现在训练集和测试集，会有什么问题？

模型可能借助训练时见过的相似序列模式取得较高测试分数，产生数据泄漏或过于乐观的泛化评估，不能代表对新蛋白质的效果。应按蛋白质或同源簇分组划分数据，并按实验方案去重和做同源过滤；调参使用验证集，测试集用于最终评估。

汇报时要准备原始数据规模、过滤后的训练和验证及测试样本数、蛋白质数量、划分方式与同源过滤阈值。当前公开仓库主要是推理服务，无法据此核实训练数据处理细节，具体数字应从论文、训练脚本和日志确认。

#### 如何说明蛋白质模型预测是否可靠？PCC 能当成准确率吗？

这是回归任务，预测的是连续的 ΔΔG，不宜直接说“准确率百分之多少”。PCC 衡量预测值与实验值的线性相关程度，PCC 为 0.69 不等于 69% 的样本预测正确；相关性高也不代表数值误差小，还应结合 RMSE 或 MAE、独立测试集和相同评估条件下的基线比较。

正向、反向和合并结果应说明各自的评估范围；ΔΔG 正负含义要和论文采用的定义一致。模型可用于辅助筛选候选突变，不能把单次输出当成实验结论。具体性能数字只引用已核对的实验表；输入格式合法，也不代表输入落在模型已验证的适用范围内。

#### 模型预测耗时如何测量和回答？

先区分首次加载模型的启动耗时和模型加载完成后的单次预测耗时，再说明硬件、设备、序列长度、突变数量、模型版本与并发条件。通过日志或计时器记录预处理、特征提取、模型计算和整体请求耗时，多次测试后报告中位数和较慢请求的表现，不能只报一次结果。

仓库文档记录过 109 个残基样例在本机 CPU 上三次 HTTP 预测约 1.4～1.9 秒；这只是文档中的小样本记录，不代表当前实验室服务器或所有序列的性能，面试前应在实际演示环境复测。

#### S3 预签名 URL 的基本原理是什么？它与 JWT 有什么区别？

S3 预签名 URL 是带有时间限制和签名的对象访问链接。后端先验证用户是否有权限，再通过 SDK 用服务端保存的访问凭证，对请求方法、对象位置、时间和有效期等内容签名。浏览器拿到链接后直接访问对象存储，由对象存储验证签名、权限和有效期，私密签名密钥不交给浏览器。

图床使用 Boto3 的 S3 Signature V4 生成 get_object 链接，有效期 600 秒。JWT 用于应用登录认证，S3 预签名 URL 用于临时授权访问指定对象，两者不是同一种机制。

#### 图片项目中的 Redis 限流采用什么算法？如何保证计数正确？

上传接口采用带过期时间的固定时长计数窗口：按用户 ID 建键，首次请求设置 60 秒有效期，窗口内最多允许 10 次上传请求，超过后返回 429 和 Retry-After。当前代码用 INCREX 原子地完成增加计数、限制上界和设置过期时间；ENX 避免每次请求都延长已有 TTL。INCREX 需要相应 Redis 版本支持。

登录接口按 IP 和用户名统计失败次数，5 次失败后暂时拒绝登录，每次失败通过 Redis 事务执行 INCR、EXPIRE，把过期时间重新设为 60 秒；成功则清零。这是失败计数加过期控制，不是严格的滑动窗口。计数增加与过期设置是原子的，但登录前检查与后续计数分开，高并发时可能超过门槛；需要严格限制时可进一步用 Lua 等方式原子校验和更新。当前 Redis 故障时记录日志并放行，需要说明其可用性与保护效果的取舍。

#### FastAPI 的异步机制有什么作用？模型推理接口应该怎么处理？

异步主要用来提高等待网络、数据库等 I/O 时的并发能力：一个请求 await 等待支持异步的操作时，事件循环可以处理其他请求。把阻塞操作直接放进 async def，并不会自动变成非阻塞，也不会让模型计算变快。

蛋白质项目的预测路由实际是普通 def，由 FastAPI 放入线程池执行，再用非阻塞锁限制一次推理；不能把它说成协程并行执行模型。计算密集、耗时较长的推理，可以按资源情况进一步使用独立模型进程或任务队列，同时考虑每个进程各自加载模型的内存或显存成本。

#### 为什么将图片元数据和对象文件分开存储？好处和代价是什么？

MySQL 保存用户、归属、对象路径、大小和创建时间等结构化元数据，便于事务、权限过滤、索引查询和分页；Garage 保存图片对象，按对象键读写，可以通过 S3 接口和临时链接访问。这样可以让数据库专注结构化业务数据，并独立管理文件存储和访问。

代价是两套系统不能靠一个 MySQL 事务保证整体原子性，需要处理失败补偿、孤立文件和备份恢复的一致性，并增加运维复杂度。当前上传流程先写 Garage，再提交 MySQL，数据库失败时回滚并尝试删除对象；补偿删除失败仍需要日志和后续处理。MySQL 并非不能存图片，而是当前需求选择分开存储更合适。

#### 可撤销的固定分享链接如何实现？撤销后临时链接也会立即失效吗？

用户为自己的图片创建分享时，后端先校验归属，再生成随机 share_token，保存在图片记录中，组成固定链接 /s/{share_token}。访问该入口时查数据库，记录有效就生成 600 秒的 S3 预签名 URL，返回 307 跳转，并设置 Cache-Control: no-store。

撤销时将 share_token 清空，原固定入口后续查询不到记录，返回 404。但已经发给浏览器的预签名 URL 由对象存储独立验证，仍可能在剩余有效期内继续使用，不能称为立即全部撤销。若要求每次访问都能立即受撤销控制，应调整为经过后端或支持逐次鉴权的访问层。当前创建和撤销由图片所属用户操作，不是只允许管理员。

#### 模型单次加载和并发保护具体如何实现？

应用启动时通过 FastAPI 的 lifespan 创建 ModelService，加载 ESM 和预测权重，并存到 app.state.service。请求通过依赖获取同一进程内已经创建的服务对象，避免每次预测都重新加载；应用关闭时调用 close 清理。

同一进程使用 threading.Lock，预测开始前 acquire(blocking=False)，获取失败直接返回 503 和 Retry-After，获取成功才执行模型，并在 finally 中释放锁，确保推理异常也不会一直占用。多个 worker 进程各自有模型和锁，不能把进程内单次加载或互斥理解成跨进程全局唯一。

#### 图床的 15 项接口测试具体覆盖哪些内容？如何证明测试有效？

当前测试文件包含 15 个测试函数：用户认证 6 项，分别是正常注册、重复用户名、重复邮箱、登录并查询当前用户、无令牌访问被拒绝、登录失败限流；图片 5 项，分别是图片完整生命周期、伪装图片拒绝、未登录上传拒绝、上传限流、用户数据隔离；健康检查 4 项，分别是应用、MySQL、对象存储和 Redis。

图片生命周期测试包括上传、列表、生成临时地址、实际下载并核对字节、删除，以及删除后旧地址不可读。每项测试应说明输入、状态码和内容断言，并以实际运行结果为准。当前这 15 项没有专门覆盖固定分享链接的创建和撤销，不能把功能已实现当成已经测过；没有真实发现并修复的缺陷案例时，应如实说明，不编造经历。
